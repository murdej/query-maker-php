# Unsupported SQL constructs

This page lists SQL constructs that QueryMaker's fluent API has **no support for at all** —
as opposed to [Known limitations](known-limitations.md), which covers things the API *does*
expose but currently renders incorrectly due to bugs. For everything below, the only way to
produce the SQL is to drop into [raw snippets](raw-sql-snippets.md) (`useSnippet()` /
`addSnippet()`) and write the fragment yourself; the library does not assist with or validate
any of it.

## Whole statement types

- **`INSERT` / `UPDATE` / `DELETE`.** `Query`/`DataSource` only ever render a `SELECT`
  statement — there is no code path anywhere in `BaseMaker` for any other statement type. This
  is a `SELECT`-only query builder.

## Clauses and modifiers within a `SELECT`

- **`SELECT DISTINCT`.** `Union::Type_Distinct` exists, but it only controls deduplication
  between `UNION` branches (`UNION` vs `UNION ALL`) — see [Unions](unions.md). There is no
  `$query->distinct` flag or equivalent for the main `SELECT` list.
- **`WITH RECURSIVE`.** `CteCollection`/`BaseMaker::makeCtes()` always emit a plain
  `WITH alias AS (...)` — the `RECURSIVE` keyword can't be added through the fluent API.
- **`INTERSECT` / `EXCEPT`.** Only `UNION` / `UNION ALL` are implemented (see
  [Unions](unions.md)).
- **Window functions** (`... OVER (PARTITION BY ... ORDER BY ...)`). No dedicated builder;
  build the whole expression as a column snippet if you need one (see
  [Raw SQL snippets](raw-sql-snippets.md)).
- **`CASE WHEN ... THEN ... ELSE ... END`.** No helper — build it as a snippet.
- **`BETWEEN ... AND ...`.** `addRange()` produces the equivalent pair of `>=`/`<=` (or `>`/`<`)
  comparisons (see [Conditions](conditions.md#addrange--inclusiveexclusive-range-with-optional-open-ends)),
  but the literal `BETWEEN` keyword is never generated by anything in the library.
- **Aggregate functions** (`SUM`, `COUNT`, `AVG`, `MIN`, `MAX`, ...). There's no
  `addSum()`/`addCount()` convenience — every example in this documentation that uses one
  (e.g. [Grouping, ordering and LIMIT](group-order-limit.md#group-by)) builds it manually via
  `addSnippet()`.
- **Locking clauses** (`FOR UPDATE`, `LOCK IN SHARE MODE`, `FOR SHARE`).
- **`CROSS JOIN`, or multiple comma-separated tables in `FROM`.** `DataSource::$from` is always
  a single table or a single sub-query; every additional table has to be expressed as a `JOIN`
  (see [Joins](joins.md)).

## Identifiers and dialects

- **Schema/database-qualified table names (`db.table`)** don't render correctly. `fromTable()`
  parses `'mydb.users u'` as one identifier with an alias, and the whole `mydb.users` ends up
  inside a single pair of backticks:

  ```php
  $query->fromTable('mydb.users u');
  ```

  ```sql
  SELECT *
  FROM `mydb.users` `u`
  ```

  That's invalid/unintended — MariaDB needs `` `mydb`.`users` `` for the identifiers to be
  parsed as database + table. There's no fluent way to express a three-part or
  database-qualified name; use a raw snippet for `FROM`/`JOIN` targets that need one.

- **Only one dialect.** `MariaDB` (backtick-quoted identifiers, MySQL/MariaDB SQL dialect) is
  the only concrete `Maker` shipped. PostgreSQL, SQLite, SQL Server, etc. are not supported at
  all — no `RETURNING`, no double-quoted identifiers, no dialect-specific `LIMIT`/`OFFSET`
  variants. You'd need to write your own `Maker` (see
  [Core concepts](core-concepts.md#writing-a-new-maker)) for another dialect, and the
  higher-level pieces (`Fulltext`'s `MATCH ... AGAINST`, `SQL_CALC_FOUND_ROWS`) are themselves
  MySQL/MariaDB-specific and would need dialect-specific replacements too.

- **Only positional `?` placeholders.** There's no support for named parameters (`:name`) —
  `$result->values` is always a plain, ordered list matched to `?` occurrences in
  `$result->query`.
